# agile-sprint-assistant 测试用例

> Creator 测试，覆盖四阶段自然使用场景。所有输入数据为 Mock，标记 TEST DATA ONLY，与生产数据严格隔离。
> 纯语义 Skill 无法自动执行断言，本文件定义"给定输入 → 期望输出特征"，作为 Claim-Evidence 证据与 Reviewer 验证依据。

---

## 场景 1：Phase 1 迭代规划（有历史速率）

### 输入（TEST DATA ONLY）

```
迭代：Sprint-27，1 周（5 工作日）
团队：
- 张三，后端，可投入 5 天，可投入率 0.8
- 李四，前端，可投入 5 天，可投入率 0.8
- 王五，后端，可投入 4 天（周三起请假 1 天），可投入率 0.8
历史速率：Sprint-24=34，Sprint-25=38，Sprint-26=36

Backlog：
- S-201 用户列表分页 P0：列表支持分页，默认每页20条，可切换10/20/50
- S-202 登录态过期跳转 P0：token 过期后跳登录页并带回跳地址
- S-203 订单导出 Excel P1：按筛选条件导出订单，含表头，≤10万行
- S-204 消息已读批量标记 P1：支持批量标记已读，接口幂等
- S-205 历史数据迁移脚本 P2：把旧表数据迁到新表，涉及未知旧表结构
```

### 期望输出特征

1. 容量计算：张三 4 人日 + 李四 4 人日 + 王五 3.2 人日 = 11.2 人日
2. 速率预测：(34+38+36)/3 = 36 故事点为本轮上限
3. 每个 Story 有故事点估算 + 依据：
   - S-201 含前端+接口 → 5 点
   - S-202 范围小 → 2 点
   - S-203 含导出+大数据量 → 8 点
   - S-204 幂等接口 → 3 点
   - S-205 含"未知旧表结构" → 高不确定性，向上取整并标注风险，可能 13+ 建议拆分
4. 圈定范围：按优先级累加，S-205 因风险/不确定可能滚动到下迭代
5. 输出含飞书多维表格字段结构（Story ID/标题/优先级/故事点/迭代/状态/依赖/风险）
6. 输出含燃尽起点（总点数、每日理想燃尽）
7. S-205 标注风险"依赖/技术"

### 验证点

- [ ] 估算每个 Story 都附依据，非凭空给数
- [ ] 高不确定性 Story 被标注风险而非强行给精确点数
- [ ] 历史速率来源明确（最近 3 轮平均）
- [ ] 输出表格字段与 references/feishu-schema.md 迭代计划表一致

## 场景 2：Phase 2 任务领取（含技能缺口）

### 输入（TEST DATA ONLY）

```
迭代：Sprint-27
Story（已圈定）：
- S-201 用户列表分页（5点）：前端列表组件 + 后端分页接口
- S-202 登录态过期跳转（2点）：前端路由守卫 + 后端 token 校验
- S-203 订单导出 Excel（8点）：后端导出接口 + 前端触发按钮 + 大数据量性能

成员技能矩阵：
- 张三：后端（强）、测试（中）
- 李四：前端（强）、设计（中）
- 王五：后端（强）
- 赵六：测试（强）  ← 本轮可投入 3 天

当前负荷：均为 0（迭代刚开始）
```

### 期望输出特征

1. 每个 Story 拆成 ≤1人日子任务（竖切）：
   - S-201 → 前端列表组件(李四) + 后端分页接口(张三/王五)
   - S-202 → 前端路由守卫(李四) + 后端token校验(张三/王五)
   - S-203 → 后端导出接口(张三/王五) + 前端触发(李四) + 性能测试(赵六)
2. 分配依据：技能匹配 + 负荷最低（初始均 0，按技能域均衡）
3. 后端任务在张三/王五间均衡，避免单人瓶颈
4. 测试任务分给赵六
5. 负荷均衡表：每人利用率，标注接近上限者
6. 若有无人匹配的任务 → 标注"技能缺口"（本场景应无，但若 S-203 需要前端大数据量虚拟滚动而李四已满 → 预警）

### 验证点

- [ ] 拆分遵循竖切（每子任务端到端可测），非横切
- [ ] 每个子任务 ≤1人日
- [ ] 分配附依据（技能匹配/负荷最低）
- [ ] 输出含负荷均衡检查表
- [ ] 未分配任务有预警和原因

## 场景 3：Phase 3 研发执行（生成 CodeArts 交付物）

### 输入（TEST DATA ONLY）

```
已领取任务：
- Story S-201 用户列表分页，迭代 Sprint-27
- 验收标准：
  AC1: 列表支持分页
  AC2: 默认每页 20 条
  AC3: 可切换 10/20/50
- 子任务：T-301 后端分页接口、T-302 前端列表组件
- 背景：当前列表一次加载全部，数据量大时卡顿
```

### 期望输出特征

1. CodeArts Story 条目：标题/类型=Story/优先级/迭代=Spring-27/故事点/描述含背景+AC+技术说明
2. CodeArts Task 条目：T-301、T-302 各一项，含所属 Story/预估工时/技能域
3. 分支名：`feature/s27-201-user-list-pagination`（符合规范：小写、连字符、≤4词简述）
4. 提交规范提示：`feat(user): 支持列表分页 S-201`
5. MR 描述模板：含变更说明/关联工作项/自测清单/验收标准映射（AC1-AC3 逐条映射）/部署影响
6. 开发自测清单：7 项通用检查

### 验证点

- [ ] 分支名严格符合 references/codearts-schema.md 规范
- [ ] MR 模板含验收标准映射（AC1/AC2/AC3）
- [ ] CodeArts 条目字段与 references/codearts-schema.md 一致
- [ ] 提交规范为 Conventional Commits

## 场景 4：Phase 4 迭代回顾（进度落后场景）

### 输入（TEST DATA ONLY）

```
迭代：Sprint-27（5 工作日）
计划故事点：30，完成故事点：21
计划 Story 5 个，完成 3 个，滚动 2 个（S-203 导出未完成、S-205 迁移未启动）
燃尽形态：理想线上方且扩大（中后期持续落后）
流水线：构建成功率 88%（2 次失败因单测未过），MR 平均合并 18 小时，缺陷 3 个
阻塞：
- S-203 大数据量导出 OOM，反复调优耗时 2 天
- S-205 旧表结构未确认，等 DBA 3 天未响应
- 临时插入 1 个线上 hotfix 占用张三 1 天
```

### 期望输出特征

1. 概览指标：完成率 70%、速率达成 21/36=58%、构建成功率 88% 等
2. 燃尽解读：形态="上方扩大"，原因=导出 OOM + 迁移等待 + hotfix 插入，建议=评估减范围/范围纪律
3. Continue：构建成功率尚可、MR 合并时长合理
4. Stop：末期插 hotfix 影响计划
5. Start：导出类需求先做性能 POC、需求依赖前置确认
6. 阻塞根因（5 Whys）：S-205 根因不止"DBA 没响应"，触及"需求依赖未在 Planning 识别"
7. 改进 Action：每项含 Owner + 验证方式（如"Planning 阶段增加依赖检查清单，Owner=Scrum Master，下迭代验证=所有 Story 标注依赖状态"）
8. 下迭代建议：速率预测下调、范围保守

### 验证点

- [ ] 燃尽形态判断正确（上方扩大=落后）
- [ ] 根因分析触及流程层面，非停在"人不够"
- [ ] 每个 Action 有 Owner + 可验证方式
- [ ] 输出结构符合 references/feishu-schema.md 回顾文档结构

## 场景 5：Phase 1 迭代规划（新团队无历史速率）

### 输入（TEST DATA ONLY）

```
迭代：Sprint-01（新团队首个迭代），2 周（10 工作日）
团队：
- 陈一，全栈，可投入 10 天，可投入率 0.7
- 陈二，前端，可投入 10 天，可投入率 0.7
历史速率：无（新团队）

Backlog：
- S-001 首页改版 P0
- S-002 用户注册流程 P0
- S-003 个人中心 P1
```

### 期望输出特征

1. 容量计算：陈一 7 人日 + 陈二 7 人日 = 14 人日
2. 速率预测：无历史 → 明确提示"无历史依据"，按容量 × 0.6 = 8.4 保守估算，强标注"速率待校准"
3. 圈定上限保守，优先圈 P0，P1 视剩余容量
4. 输出明确标注"本轮速率为保守估计，实际速率需 2-3 轮迭代后校准"

### 验证点

- [ ] 无历史速率时明确提示，不假装有依据
- [ ] 应用容量 × 0.6 保守规则（references/agile-knowledge.md 速率预测规则）
- [ ] 输出含"速率待校准"标注

## 场景 6：模糊/不完整输入处理

### 输入（TEST DATA ONLY）

```
用户只粘贴了需求标题，无优先级、无团队、无容量：

迭代规划帮我排一下：
- 用户列表分页
- 登录跳转
- 订单导出
```

### 期望输出特征

1. 识别为 Phase 1（触发词"迭代规划/排"）
2. 检测到必要字段缺失：无优先级、无团队、无容量、无历史速率
3. 按 SKILL.md 核心原则第 5 条：先提示用户补全必要字段（团队/容量/优先级），不静默编造
4. 可对已有信息做部分处理：对 3 个标题给出初步故事点估算建议（标注"基于标题推断，待补充描述后细化"）
5. 不强行输出完整迭代计划（因缺关键输入）

### 验证点

- [ ] 缺必要字段时提示补全，不静默编造数据
- [ ] 不因输入不完整而拒绝服务，对可处理部分给出标注假设的初步结果
- [ ] 符合 SKILL.md 核心原则第 5 条

## 测试覆盖总结

| 阶段 | 场景 | 覆盖的自然维度 |
|------|------|---------------|
| Phase 1 | 有历史速率的迭代规划 | 估算/速率/圈定/风险标注 |
| Phase 1 | 新团队无历史速率 | 无历史速率保守估算/速率待校准标注 |
| Phase 2 | 含技能缺口的任务领取 | 竖切拆分/技能匹配/负荷均衡/预警 |
| Phase 3 | 生成 CodeArts 交付物 | Req条目/分支/提交/MR/自测清单 |
| Phase 4 | 进度落后的迭代回顾 | 指标计算/燃尽解读/根因/Action |
| 跨阶段 | 模糊/不完整输入 | 必要字段缺失提示/标注假设/不编造 |

覆盖了结构化 Happy Path（场景 1-4）、无历史速率边界（场景 5）、模糊输入健壮性（场景 6）。未覆盖的自然维度（迭代长度可变、跨迭代依赖）在 references 中有规则支撑，Reviewer 可按规则验证。
