## 故事点估算（Story Point Estimation）

### 为什么用故事点而非人日

故事点度量"复杂度+不确定性+工作量"的相对规模，与具体人无关，便于跨成员速率统计。人日因人而异，不利于速率稳定性。

### Modified Fibonacci 数列

常用数列：1, 2, 3, 5, 8, 13, 21。相邻差距随规模增大而增大，体现大任务估算不确定性。

### 估算方法

1. **基准故事法（推荐）**：先选一个大家都理解的中等故事定为基准（如 5 点），其余与之比较
2. **Planning Poker**：成员各自出牌后讨论分歧，收敛。分歧大说明需求未澄清
3. **类比历史**：与历史相似 Story 对比

### 估算建议生成规则

- 需求描述含明确接口/数据模型/页面数 → 按数量加权
- 含"未知第三方/性能要求/历史数据迁移" → 不确定性高，向上取整并标注风险
- 超过 13 → 建议拆分
- 无法估算 → 标注"需澄清"，不强行给数

## 速率（Velocity）与迭代容量

### 容量计算

```
迭代容量 = Σ(成员可投入天数 × 可投入率)
可投入率 = 1 − (会议/请假/支援/上下文切换损耗)
典型可投入率：0.6 ~ 0.8
```

### 速率预测

- 有 ≥3 个历史迭代速率：取最近 3 个的平均，作为本轮圈定上限
- 历史 < 3 个：用容量 × 0.7 作为保守起点，并明确提示"速率待校准"
- 无历史：明确提示无历史依据，按容量 × 0.6 保守估算，强标注

### 圈定范围

按优先级从高到低累加故事点，直到接近速率上限。剩余进下迭代。若最高优先级单项已超速率，标注"需拆分或调速率"。

### 跨迭代依赖处理

当 Story 依赖尚未完成的其他 Story（可能在本迭代或下迭代）时：

| 依赖状态 | 处理方式 |
|----------|----------|
| 依赖在本迭代内、可并行 | 标注依赖关系，建议被依赖项先启动 |
| 依赖在本迭代内、无法并行 | 标注"强依赖"，建议拆出可独立交付的子部分先做 |
| 依赖在下迭代 | 标注"跨迭代依赖"，建议：① 调整顺序把被依赖项提前；② 或拆分出本迭代可独立交付的最小切片；③ 若无法拆分则滚动到下迭代 |

原则：尽量保证本迭代每个 Story 可独立交付可演示价值，避免因跨迭代依赖导致整批滚动。

## 迭代中范围变更与插单处理

迭代进行中常遇插单/范围变更，本节给出评估与决策建议框架（Skill 给建议，最终由 PO/团队拍板）。

### 插单评估三问

| 问题 | 判断依据 | 若是 / 若否的处理 |
|------|----------|-------------------|
| ① 是否 P0？ | 不做完会阻塞上线 / 线上故障 | 是 → 进入插单流程；否 → 进下迭代 Backlog |
| ② 是否可拆出 ≤2 人日的最小可交付切片？ | 能否独立交付可演示价值 | 是 → 本迭代插入该切片，其余进下迭代；否 → 评估是否值得打断当前迭代 |
| ③ 团队是否有人有 buffer？ | 利用率 < 80% | 是 → 分配给该人；否 → 必须换出等点数或等价值的低优先级项 |

### 换出决策建议

- 从本迭代未启动的 Story 中，按优先级从低到高、故事点最接近插单项的候选换出
- 换出项需标注"因插单 S-XXX 滚动到 Sprint-(N+1)"
- 若插单项点数 > 所有可换出项总和，提示"需 PO 决策：是否缩减插单范围或延长迭代"，不替决策

### 范围变更沟通流程

1. 插单提出者在飞书群 / @PO 说明背景 + 紧急性 + 期望完成时间
2. Skill 协助评估三问，输出"插入 / 换出 / 进下迭代"建议
3. PO 拍板，飞书多维表格更新迭代字段、看板状态
4. 若换出，原 Story 负责人同步释放，插单项重新走 Phase 2 任务领取

原则：插单是常态不是例外，关键是有评估框架而非情绪化决策；频繁插单（>2 次/迭代）应在回顾时讨论范围纪律。

## Story 拆分原则

### INVEST 检查

Independent / Negotiable / Valuable / Estimable / Small / Testable。不满足 Small 或 Estimable → 拆分。

### 竖切优于横切

- **竖切（推荐）**：按用户可感知的功能端到端切片（如"列表展示"含前端+接口+数据）
- **横切（避免）**：按技术层切（如"先做所有接口"），导致迭代末期才有可演示价值

### 拆分到可估算粒度

目标：子任务 ≤ 1 人日（或 ≤ 3 故事点）。拆分后每项仍独立可测。

## DoD（Definition of Done）

典型 DoD 清单（团队可裁剪）：
- 代码已提交并通过本地自测
- MR 已通过至少 1 人 Review
- CI 流水线全绿
- 单元测试覆盖新增逻辑
- 验收标准全部满足
- 文档/接口说明已更新

## 燃尽图（Burndown）解读

| 形态 | 含义 | 建议 |
|------|------|------|
| 理想线下方 | 进度超前 | 可考虑加入低优先级 Story |
| 贴合理想线 | 进度健康 | 维持 |
| 理想线上方且扩大 | 进度落后 | 评估是否减范围或加人 |
| 中途陡降 | 范围被砍或故事点重估 | 记录原因 |
| 末期突增 | 末期加需求 | 回顾时讨论范围纪律 |

## 迭代回顾方法

### Start / Stop / Continue

- **Start**：下迭代开始做什么
- **Stop**：停止做什么（无效实践）
- **Continue**：继续做什么（有效实践）

### 5 Whys 根因分析

对每个阻塞/未完成项，连续问"为什么"直到触及流程根因，而非停在"人不够"。

### 改进 Action 要求

每个 Action 必须含：具体动作 + Owner + 下迭代如何验证生效。无 Owner 或无法验证的 Action 视为无效。

## 负荷均衡

### 原则

- 同技能域内尽量均衡，避免单人成为瓶颈
- 考虑上下文切换成本：同一人尽量集中同类任务
- 保留 ~20% buffer 应对临时插单/支援

### 分配建议生成规则

1. 按技能匹配筛选候选人
2. 在候选人中选当前负荷最低者
3. 若分配后某人负荷 > 容量 × 0.9，标注"接近上限"
4. 无人匹配 → 标注"技能缺口"，不强行分配
